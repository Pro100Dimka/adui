Изменены подтверждённые пути: сортировка DataTable, сборка dev-runtime предпросмотра, загрузка исходников редактором документации, общий animation scheduler, NeonWaves и QuantumField. Это измеренные локальные улучшения, а не доказательство максимальной производительности всей библиотеки.

## Среда и метод

Windows 10 Pro 10.0.19045; Intel Core Ultra 7 265KF, 20 логических процессоров; 32 ГиБ RAM; NVIDIA RTX 3060; Node 22.23.2; Chrome 156.0.8078.80 headless. Активный план питания — «Экономия энергии», настройки системы не менялись. Температура и частоты не записывались; фоновые приложения не отключались.

DataTable: production React, детерминированные числовые значения `(index * 7919) % count`, сортировка последней колонки, страница из 10 строк. Измеряется сортировка вместе с серверным рендером, без браузерной отрисовки. Три прогревочных прохода и 100 измерений. Повторная серия выполнена в обратном порядке: сначала изменённая версия, затем исходная. Таблица ниже использует эту подтверждающую серию. SHA-256 полной HTML-разметки совпал для каждой размерности.

Runtime: HTTP localhost, чтение всего ответа размером 2 417 275 байт, 20 повторений после первого запроса. Параллельный сценарий — шесть запросов в пакете. Результаты относятся к dev-серверу.

Редактор: production-сборка, новое браузерное окружение для каждого CPU-профиля, первое и пять повторных открытий InputBase → «Код». Проверялось появление Monaco и работающего iframe. Профили CPU ×4 и ×6 — эмуляция замедления на том же компьютере. Реальные слабый и средний ПК не проверялись. В повторном exploratory-прогоне часть работы могла пересечься с тестами, поэтому сравнение времени редактора не считается доказательством ускорения.

## Причины и изменения

- `DataTable.tsx`: поиск колонки выполнялся внутри каждого сравнения сортировки. Колонки теперь разрешаются один раз перед сортировкой в существующем `useMemo`. Не менялись компаратор, стабильность, NaN, multi-sort, ручная сортировка, пагинация и API. Регрессионный тест до исправления насчитал 787 012 чтений ключей при 2 000 строках и 40 колонках.
- `vite.config.ts`: каждый запрос пересобирал один и тот же runtime. Сохраняется одна общая Promise сборки, включая одновременные запросы. Любое событие watcher сбрасывает кеш; ошибка допускает повторную попытку. Цена — удержание одной строки runtime в памяти dev-сервера. Полная стоимость памяти не измерялась.
- `CodeEditor.tsx`, `sources.ts`: IntelliSense использовал отдельные dynamic imports исходников, уже загружаемых документацией. Теперь используется существующий пакет исходников с теми же исключениями example/meta/dev. React-типы и TypeScript worker сохранены.

Переиспользование iframe не внедрялось: новый iframe сохраняет изоляцию и очистку состояния примера. Переписывание Monaco, новый планировщик, GPU offload сортировки и дополнительные потоки не вводились без сравнительных измерений.

## Архитектура и ограничения

Это React-библиотека и Vite-документация, собственного backend и Electron IPC здесь нет. Уже реализованы общий motion clock, пауза невидимых и скрытых эффектов, Worker для обводок, WebGL с Canvas fallback, ограничение pixel/particle budget, переиспользование аудиобуферов, виртуализация/пагинация DataTable, отмена устаревших поисков. Эти механизмы не дублировались. NUMA, VRAM-offload, mixed precision и модельные вычисления к изменённым путям не относятся. Живая запись, underrun, реальная iGPU, CPU-only браузер, дисковая нагрузка и утечки при длительной работе не проверялись.

Корректность сортировки проверена существующими сценариями и новым тестом числа обращений; HTML сравнивался по SHA-256. Тест runtime проверяет общий concurrent build, кеш, инвалидирование и восстановление после ошибки. Дополнены переводы описания InputBase, обнаруженные полным прогоном. Изменения визуального оформления полей выполнялись отдельно по уточнениям и не включены в заявленный выигрыш сортировки.

## Анимации и компоненты: CPU ×8 и ×16

Уточнение воспроизводимости: в первоначальном benchmark проверка подстановки TSX/CSS отсутствовала, а фильтр путей учитывал только `/`. На Windows эта серия не доказывает сравнение с полностью исходными компонентами: подстановка трёх JS-файлов движка не зависит от разделителя, подстановка TSX/CSS не была подтверждена. Старые raw данные сохранены, но их нельзя использовать как строгое сравнение полного исходного и конечного состояния компонентов. Для нового этапа MelodyRoll фильтр исправлен, имена подставленных файлов записываются и проверяется их количество.

Контролируемое замедление Chrome через CDP, а не реальные слабые компьютеры. Production React, viewport 1440×1000, тот же компьютер и план питания. Сценарии: 30 TextField; 90 AnimatedBorder; 6 NeonWaves вместе с 6 LevelMeter; один QuantumField 1400×500. Прогрев: готовность worker canvases и ещё 1200 мс; измерение — 3 секунды. До изменений — три повтора; после — два для полей, обводок и QuantumField, три для композиции. Это короткие steady-state пробы, не длительная гарантия FPS и не измерение холодного открытия.

Исправления:

- Общий clock и workers по умолчанию получают цель 60 вместо 20/30 fps. При 60 убрано дополнительное ожидание таймера перед requestAnimationFrame. Явный `setMotionFrameRate(30)` и остановка скрытых/неиспользуемых эффектов сохранены.
- NeonWaves рисует звёзды в существующем worker вместе с волнами. Позиции, размеры, девять фаз и CSS ease-in-out сохранены. При отсутствии worker canvas действует CSS fallback с девятью группами вместо 60 отдельных анимаций. Пауза вне экрана охватывает корневой элемент, включая звёзды.
- QuantumField больше не ограничивает WebGL собственными 24/30 fps. Допуск 0,5 мс предотвращает пропуск кадров из-за округления timestamps. CPU fallback сохраняет прежнее ограничение; QuantumBackground остаётся отдельным адаптивным визуализатором.

Частота общего clock измерена отдельно; у QuantumField дополнительно считались реальные вызовы очистки WebGL canvas: после изменений около 60/с на обоих уровнях замедления против примерно 20–21/с до изменений. Переход на более частое обновление сам по себе увеличивает работу: на ×16 медиана main thread для полей выросла 1522 → 1947 мс (+27,9%), обводок 1556 → 2252 мс (+44,7%), QuantumField 1449 → 1952 мс (+34,7%). На ×8 соответствующие изменения: 520 → 672 (+29,2%), 537 → 742 (+38,2%), 411 → 730 мс (+77,6%). Это плата за частоту, а не снижение CPU. При 90 обводках на ×8 появились пропущенные кадры по сравнению с baseline; общий clock при этом обновлялся значительно чаще. Для приложений, предпочитающих меньше декоративной работы, остаётся явная настройка частоты.

Отброшенные варианты: одно увеличение частоты перегружало CSS-звёзды; группировка уменьшила нагрузку, но на ×16 оставалась недостаточной. `will-change` для звёзд/групп, CSS transform индикатора и отключение его фильтра не стали производственными изменениями. Перенос звёзд в существующий worker устранил этот bottleneck. До переноса проверены 180 значений композиционной opacity: максимальное отличие от прежнего CSS — менее 0,000001. Worker отдельно проверяется по координатам, размеру и значениям easing в начале, середине и конце цикла.

Ограничения: непрерывные минимум 60 fps не достигнуты во всех стресс-сценариях. Есть отдельные длинные кадры, включая 133 мс в композиции на ×16. Одна промежуточная серия прервалась по тайм-ауту готовности 90 обводок; последующая серия из двух повторов завершилась, тайм-аут не считается успешной проверкой. CPU-only диагностический прогон QuantumField на ×16 дал около 21 кадра отрисовки/с и 34 rAF/с; его нельзя выдавать за 60 fps. GPU/VRAM utilization, пиковая RAM, реальные iGPU/малоядерные устройства, event-to-paint latency и длительная стабильность не измерены. JS heap в raw JSON — моментальный снимок, не пик памяти. Частота пиксельной отрисовки OffscreenCanvas workers отдельно не измерена.

## MelodyRoll

Найдена и изменена существующая реализация `packages/ui/src/components/media/MelodyRoll`: два производственных файла, 35 добавленных и 12 удалённых строк. Клавиатура уже использовала memo; новый компонент или отдельный планировщик не добавлялись.

На каждом playback update раньше создавался массив всех pitch, пересчитывались границы и фильтровалась вся песня. Теперь при смене `notes` рассчитываются pitch bounds и временные границы блоков по 128 нот; кадр проверяет только потенциально видимые блоки. Исходный порядок и длинные перекрывающиеся ноты сохраняются. Для хаотично перемешанных нот худший случай остаётся линейным. Массив и его ноты должны обновляться иммутабельно. Лента привязана к ближайшему временному окну, чтобы координаты обычных нот не росли вместе с длительностью песни.

Главный браузерный bottleneck — RecalcStyle при постоянно меняющихся beat/accuracy/level. Точность и громкость перенесены с корня на след и маркер голоса. Beat зарегистрирован как ненаследуемое числовое свойство, с явной передачей двум использующим его псевдоэлементам. Остальные ноты и клавиши не наследуют эти обновления. Свечение, переходы, попадания, текст, колесо и диапазоны высоты сохранены. Отключение transitions давало дополнительное ускорение, но этот вариант не принят из-за изменения визуального поведения.

Сценарий: один MelodyRoll 1400×400, 10 000 нот с шагом 0,25 с, длительностью 0,2 с и диапазоном 60–71 MIDI; около 32 видимых нот, lyrics включены. Position, livePitch, accuracy, level и beat обновляются общим clock. Production React, Chrome и компьютер те же. CPU ×8/×16 — эмуляция. Два прогретых окна примерно по 3 секунды на каждую частоту, в подтверждающей серии сначала итоговая версия, затем baseline. Baseline подставляет **только MelodyRoll.tsx и styles.css из HEAD**, проверяет наличие обоих файлов; общий scheduler одинаков. `rendererFrames` в этом сценарии считает React commits, не физические презентации GPU.

Повторная сборка и suite на этом диагностическом этапе не запускались, поскольку производственные изменения экспериментов отменены.

В трассе пересчёт стилей затрагивает около 21–23 элементов. Аппаратная композиция и растеризация включены; активный ANGLE renderer использует NVIDIA RTX 3060/D3D11. Причина не сводится к отсутствию GPU.

Изучены [обсуждение SVG drop-shadow](https://stackoverflow.com/questions/19565622/css-animation-performance-issues-using-svg-drop-shadow-filter) и [обсуждение box-shadow в Lighthouse](https://github.com/GoogleChrome/lighthouse/issues/15560). Советы про статическое свечение и анимацию opacity требуют проверки визуальной эквивалентности: замена меняющегося радиуса размытия прозрачностью постоянной тени изменяет эффект. Такая замена не принята.

Проверены дополнительные `will-change`, containment, прямой transform секундной сетки, memoization частей компонента и перенос вертикального движения маркера на translate. Убедительного прироста полного сценария они не дали; производственная реализация после этой серии сохранена без этих изменений. Незавершённый прототип canvas renderer удалён. Новый прирост производительности не заявляется; цель 60 FPS на ×16 остаётся недостигнутой. Следующая проверяемая гипотеза — кэширование/отрисовка динамического свечения вне основного потока с сохранением его формы, цветов и переходов; визуальная эквивалентность такого подхода пока не доказана.

## MelodyRoll: worker для свечения и повторное использование нот (после 1.3.9)

Изучена существующая реализация и сохранены её три слоя дорожки, свечение, ноты, клавиши, текст и hit-эффекты. SVG содержит по три обводки на непрерывный участок голоса; ноты и клавиши являются HTML/CSS. Удаление точек или слоёв не использовалось. Изолированный перенос beat-свечения помог, но одного переноса отрисовки оказалось недостаточно для полного сценария. В трассировке оставались обновления стилей и layout при изменении набора нот. Два соседних временных окна позволяют повторно использовать элементы и геометрию нот; JSX обновляется при смене видимости, фазы или попадания. При недоступном worker сохраняется прежний диапазон DOM-нот.

Общий worker рисует через OffscreenCanvas внешнее и внутреннее beat-свечение, голосовой маркер и дорожку. Три поверхности сохраняют порядок слоёв относительно нативного playhead. Цвета, размеры и длительности читаются из CSS при настройке; на каждом кадре чтения computed styles нет. Сохранены линейное движение маркера, CSS ease для размера и цвета, сокращение обратного перехода и hit-пульс. Правило обратного перехода сверено с [CSS Transitions](https://www.w3.org/TR/css-transitions/#reversing). Видимость документа, viewport, pause и reduced motion учитываются; последний unmount завершает worker и освобождает URL. При ошибке или отсутствии необходимых API возвращается CSS/SVG. Некоторые нестандартные CSS-формы также требуют fallback; произвольные переопределения CSS во всех браузерах не проверены.

## Повторная диагностика основного потока на ×16

**Нового воспроизводимого ускорения в этой серии не получено; производственные эксперименты отменены.** Реализация MelodyRoll, CSS и worker возвращены к состоянию начала этой серии, а не к релизу 1.3.9. Предыдущая работа с worker сохранена. Совпадение трёх исходных файлов проверено после нормализации переводов строк; их SHA-256 записаны в `melodyMainThreadInvestigation` файла `performance-results.json`.

В Chrome trace найдены причины отказа от compositor-анимации: 34 события `4096` для фильтров нот, 35 событий `8224` с неподдерживаемым `color` у клавиш и 26 событий `131072` без видимого изменения. Значение `4096` соответствует фильтрам, которые расширяют область пикселей; `drop-shadow` остаётся на основном потоке. Нумерация и проверка свойств сверены с [перечнем причин Chromium](https://chromium.googlesource.com/chromium/src/+/59c1b7deb132b7478bb27f2f7b773b1b71236e5d/third_party/blink/renderer/core/animation/compositor_animations.h) и [проверкой filter](https://chromium.googlesource.com/chromium/src/+/079ad5b81506fb387ec158e184ff95535c3b9f92/third_party/blink/renderer/core/animation/compositor_animations.cc). Поэтому простое добавление `will-change` не решает этот путь.

В профиле основного потока `UpdateLayoutTree` занял около 1132 мс, `Paint` — 897 мс, `FunctionCall` — 1351 мс; один layout — 233 мс. События вложены, их нельзя складывать как независимые затраты. Трассировка влияет на частоту кадров и не использована как контроль для обычного FPS-прогона. Worker в этой трассировке не является единственным или основным источником задержек основного потока.

Короткие изолирующие прогоны ×16, по 5 секунд (диагностика, не варианты для поставки):

| Остановлена отрисовка worker, DOM продолжает обновляться | 12,91 | 117 мс |

Это локализует оставшуюся стоимость в обновлении и перерисовке DOM нот/клавиш, вместе с React и браузерным lifecycle. Это не точное разложение процентов стоимости: серии последовательные, разброс большой. Даже отключение всех transitions в диагностике не довело полную сцену до 60 FPS. Эффекты в производственном коде не отключены и не упрощены.

Проверены и отменены: `contain: layout style`, paint containment, дополнительное продвижение canvas в слои, сохранение прошлой фазы скрытых нот и пропуск отрисовки неизменившейся дорожки. Ранние 22–23 FPS с containment не подтвердились: повтор дал 9,03–10,16 FPS на ×16 против 15,18–17,84 у сохранённой исходной версии этой серии. Отдельный вариант только с кешированием дорожки дал 10,27–10,43 FPS; его также отменили. Контроль ×8 в подтверждающей серии — 55,71–56,51 FPS. Сравнение установившегося кадра дорожки с разрывом на тишине дало 0 изменённых пикселей; отсутствие визуальных различий не заменяет доказательство ускорения.

Benchmark теперь явно ждёт готовности worker перед прежним прогревом 1200 мс. Так начальный переход CSS → worker исключается из steady-state сравнения. `FRAME_PAUSE_GLOW=1` предназначен только для диагностики. `FRAME_MELODY_REFERENCE=<directory>` подставляет сохранённые `MelodyRoll.tsx`, `styles.css`, `melody-glow.js` и проверяет загрузку всех трёх файлов. Окончательное сравнение: ×8/×16, два повтора по 10 секунд, все эффекты включены. Raw результаты всех гипотез, включая неудачные, сохранены отдельно от предыдущей серии. Без такого доказательства замена этих эффектов кроссфейдами или урезанным свечением не включалась. **Стабильные 60 FPS всё ещё не достигнуты.**

## MelodyRoll: ноты, текст и эффекты клавиш в worker (следующая нерелизная ревизия)

Перенос выполнен в существующем общем worker: добавлены поверхности нот/секундной сетки и клавиш, сохранён порядок относительно дорожки и playhead. Нативные кнопки клавиатуры остаются для ввода и фокуса. После готовности worker DOM-ноты удаляются, а структурное JSX-дерево не обновляется на каждом playback tick. Набор нот передаётся только при смене двух соседних временных окон; `hitIds` проверяется и при изменении существующего Set. Геометрия, градиенты, тени, шрифты и длительности берутся из CSS при настройке. Установившееся воспроизведение не читает computed styles и не вызывает layout/style recalculation.

Растровые заготовки ограничены 512 исходными спрайтами и 8 × 1024² физическими пикселями кеша фильтрованных нот (около 32 МиБ RGBA; это не предел всей памяти сцены/GPU). Кеш очищается при перенастройке. Фильтры применяются до масштабирования вспышки: [Canvas filter](https://html.spec.whatwg.org/multipage/canvas.html#filters) не масштабируется текущей матрицей. Сохранены порядок перекрывающихся нот, opacity прошлых нот, дискретная смена несовместимых списков фильтров, CSS easing, hit-scale и пульсация/нажатие/hover клавиш. Текст измеряется по нативной baseline; доступные `@font-face` загружаются через FontFace в worker до handoff. Неподдерживаемая типографика/границы и недоступные источники шрифтов возвращают нативную отрисовку. Ошибки асинхронной настройки также возвращают CSS/SVG.

Дополнительный stress: 30 секунд со всеми hitIds и активной hit-клавишей. Сборки/тесты не запускались одновременно с этими замерами.

Экстраполяция позиции не добавлялась: она изменила бы контракт контролируемого `position`. Поле `displayFps` в benchmark означает main-thread rAF, а не физическую частоту презентации GPU. Новое поле `worker` измеряет отдельный rAF-цикл. CDP ×8/×16 замедляет поток страницы, а не все ядра/GPU: это видно по [реализации Emulation](https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/core/inspector/inspector_emulation_agent.cc) и [ThreadCPUThrottler](https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/platform/scheduler/common/thread_cpu_throttler.cc). Поэтому результат не является гарантией 60 FPS на устройстве с процессором в 16 раз слабее.

### Внешний вид и проверки

Сопоставлены одинаковые статические кадры с предыдущей реализацией, пик вспышки ноты (173,6 мс), кадр hit-клавиши/маркера (189 мс), синяя тема при DPR 2. Для анимационных кадров диагностический код фиксирует время worker и заново запускает нативные CSS-анимации на той же фазе; эта фиксация не входит в производственный код или FPS-прогоны. Средняя абсолютная разница RGB по всему изображению: 0,103 / 0,291 / 0,100 / 0,156 из 255 соответственно. Это не побитовое совпадение: у Canvas/CSS различается сглаживание текста, границ и теней, особенно при DPR 2. Средняя разница в области клавиатуры отдельно записана в raw-результатах, чтобы большой пустой фон не скрывал её. Эффекты и их интенсивность намеренно не сокращались.

Браузерные проверки: Enter вызывает обработчик ровно один раз и сохраняет фокус; смена диапазона/позиции/window, resize, цвета и webfont сохраняют worker; reduced motion работает; отсутствие Worker и принудительная ошибка возвращают DOM-ноты/SVG; unmount оставляет 0 canvas и завершает созданный worker ровно один раз. Контрактные проверки покрывают передачу изменяемого hitIds, ограниченный набор нот, их порядок при перекрытии, масштабирование отфильтрованного hit-спрайта, пульсацию/нажатие клавиши, паузу и ошибку настройки.

`npm run check`: TypeScript, обе production-сборки, 620 тестов в 41 файле. После уточнения обработки асинхронной ошибки повторно прошли 16 MediaContracts и синтаксические проверки worker/benchmark. Релиз и обновление потребителей не выполнялись. Raw-данные этой серии находятся в `melodyForegroundWorker` файла `performance-results.json`; предыдущие серии сохранены.

Финальное подтверждение после правок обработки ошибок: ×16, 20 секунд, main rAF 59,10 FPS, p95 16,8 мс, p99 33,3 мс, максимум 49,8 мс; worker 60,03 FPS, максимум 17,2 мс. Одна настройка worker, 0 мс layout/style, ошибок страницы нет. Финальная production-сборка библиотеки прошла.


## Зависания live pitch при изменении стилей (1.3.12)

Причина воспроизведённых секундных остановок: MutationObserver на style корня/предков запускал полное измерение CSS клавиш при каждом обновлении декоративной переменной. Проверка сигнатуры происходила уже после дорогих чтений стилей и layout. Теперь изменения сравниваются с предыдущим inline style, зависимости CSS-переменных учитывают цепочки var(), а неиспользуемые переменные не вызывают повторную настройку. Нативная тень корня при beat=0 обновляется средствами CSS; при возобновлении beat отложенные изменения измеряются. Нечитаемые таблицы стилей сохраняют консервативный путь. Изменения темы, диапазона и размеров по-прежнему перенастраивают renderer. Повторные сообщения неизменившейся видимости исключены.

В караоке stageFxRenderer обновляет --show-roll-glow на корне MelodyRoll. Переменная используется только тенью этого корня; регистрация @property с inherits:false сохраняет её числовое значение и исключает ненужное наследование всем потомкам. Это соответствует [измерениям Chrome для @property](https://web.dev/blog/at-property-performance?hl=en). Другая отрисовка, интенсивность эффектов и сглаживание пича не изменены.

Production fixture: 10 000 нот, 1400×400, DPR 1; пич меняется с частотой 50 Гц, присутствуют короткие паузы. Сценарий караоке воспроизводит внешний CSS и изменяемую переменную, а не полный запуск приложения с микрофоном. После исправления — 10 секунд на каждую скорость; до исправления запрошено 5 секунд, но блокировки продлили фактические измерения до 5,27/6,95 секунды.

| Сценарий | ×8 main rAF FPS | ×16 main rAF FPS | ×16 максимальный интервал |
| --- | ---: | ---: | ---: |
| Караоке-стили до исправления | 1,52 | 0,43 | 2599,9 мс |
| Караоке-стили после исправления и регистрации переменной | 59,20 | 16,74 | 133,3 мс |
| Обычный MelodyRoll после исправления | 59,70 | 59,00 | 33,5 мс |

После исправления в установившемся сценарии караоке нет повторных чтений computed styles настройщиком; worker rAF на ×16 — 60,01 FPS. Это не означает 60 обновлений входного пича в секунду: основной поток с нативной анимированной тенью остаётся ограничением. Стабильные 60 FPS для караоке на ×16 не достигнуты. CDP замедляет поток страницы, а worker rAF и main rAF не измеряют физическую презентацию GPU.

Браузерная регрессия FRAME_VERIFY_STYLE_TICK падает на сохранённом исходнике и проходит после исправления. Смена CSS-алиаса цвета, диапазона, resize, Enter/focus и освобождение worker/canvas проверены. Статические PNG до/после при одинаковой фазе совпали побайтово (SHA256 B2D3871541FD3E0292C6460BDD075FE20C05E535AA04A61D9B4A7FE94025E2FA). Это проверка одного кадра, а не всех анимационных фаз.

Полная проверка фронтенда караоке выявила отдельное падение useEditorPreview.test.tsx: ожидалась позиция 7, получено undefined. Хук редактора уже изменён в рабочей копии вне этой правки; полная проверка приложения не считается успешной. Реальное пение с микрофоном в этой серии не проверялось. Raw-результаты находятся в melodyPitchStyleInvalidation файла performance-results.json.
