Изменены подтверждённые пути: сортировка DataTable, сборка dev-runtime предпросмотра, загрузка исходников редактором документации, общий animation scheduler, NeonWaves и QuantumField. Это измеренные локальные улучшения, а не доказательство максимальной производительности всей библиотеки.

## Среда и метод

Windows 10 Pro 10.0.19045; Intel Core Ultra 7 265KF, 20 логических процессоров; 32 ГиБ RAM; NVIDIA RTX 3060; Node 22.23.2; Chrome 156.0.8078.80 headless. Активный план питания — «Экономия энергии», настройки системы не менялись. Температура и частоты не записывались; фоновые приложения не отключались.

DataTable: production React, детерминированные числовые значения `(index * 7919) % count`, сортировка последней колонки, страница из 10 строк. Измеряется сортировка вместе с серверным рендером, без браузерной отрисовки. Три прогревочных прохода и 100 измерений. Повторная серия выполнена в обратном порядке: сначала изменённая версия, затем исходная. Таблица ниже использует эту подтверждающую серию. SHA-256 полной HTML-разметки совпал для каждой размерности.

Runtime: HTTP localhost, чтение всего ответа размером 2 417 275 байт, 20 повторений после первого запроса. Параллельный сценарий — шесть запросов в пакете. Результаты относятся к dev-серверу.

Редактор: production-сборка, новое браузерное окружение для каждого CPU-профиля, первое и пять повторных открытий InputBase → «Код». Проверялось появление Monaco и работающего iframe. Профили CPU ×4 и ×6 — эмуляция замедления на том же компьютере. Реальные слабый и средний ПК не проверялись. В повторном exploratory-прогоне часть работы могла пересечься с тестами, поэтому сравнение времени редактора не считается доказательством ускорения.

## Причины и изменения

- `DataTable.tsx`: поиск колонки выполнялся внутри каждого сравнения сортировки. Колонки теперь разрешаются один раз перед сортировкой в существующем `useMemo`. Не менялись компаратор, стабильность, NaN, multi-sort, ручная сортировка, пагинация и API. Регрессионный тест до исправления насчитал 787 012 чтений ключей при 2 000 строках и 40 колонках.
- `vite.config.ts`: каждый запрос пересобирал один и тот же runtime. Сохраняется одна общая Promise сборки, включая одновременные запросы. Любое событие watcher сбрасывает кеш; ошибка допускает повторную попытку. Цена — удержание одной строки runtime в памяти dev-сервера. Полная стоимость памяти не измерялась.
- `CodeEditor.tsx`, `sources.ts`: IntelliSense использовал отдельные dynamic imports исходников, уже загружаемых документацией. Теперь используется существующий пакет исходников с теми же исключениями example/meta/dev. React-типы и TypeScript worker сохранены.

Переиспользование iframe не внедрялось: новый iframe сохраняет изоляцию и очистку состояния примера. Переписывание Monaco, новый планировщик, GPU offload сортировки и дополнительные потоки не вводились без сравнительных измерений.

## Архитектура и ограничения

Это React-библиотека и Vite-документация, собственного backend и Electron IPC здесь нет. Уже реализованы общий motion clock, пауза невидимых и скрытых эффектов, Worker для обводок, WebGL с Canvas fallback, ограничение pixel/particle budget, переиспользование аудиобуферов, виртуализация/пагинация DataTable, отмена устаревших поисков. Эти механизмы не дублировались. NUMA, VRAM-offload, mixed precision и модельные вычисления к изменённым путям не относятся. Живая запись, underrun, реальная iGPU, CPU-only браузер, дисковая нагрузка и утечки при длительной работе не проверялись.

Корректность сортировки проверена существующими сценариями и новым тестом числа обращений; HTML сравнивался по SHA-256. Тест runtime проверяет общий concurrent build, кеш, инвалидирование и восстановление после ошибки. Дополнены переводы описания InputBase, обнаруженные полным прогоном. Изменения визуального оформления полей выполнялись отдельно по уточнениям и не включены в заявленный выигрыш сортировки.

## Анимации и компоненты: CPU ×8 и ×16

Уточнение воспроизводимости: в первоначальном benchmark проверка подстановки TSX/CSS отсутствовала, а фильтр путей учитывал только `/`. На Windows эта серия не доказывает сравнение с полностью исходными компонентами: подстановка трёх JS-файлов движка не зависит от разделителя, подстановка TSX/CSS не была подтверждена. Старые raw данные сохранены, но их нельзя использовать как строгое сравнение полного исходного и конечного состояния компонентов. Для нового этапа MelodyRoll фильтр исправлен, имена подставленных файлов записываются и проверяется их количество.

Контролируемое замедление Chrome через CDP, а не реальные слабые компьютеры. Production React, viewport 1440×1000, тот же компьютер и план питания. Сценарии: 30 TextField; 90 AnimatedBorder; 6 NeonWaves вместе с 6 LevelMeter; один QuantumField 1400×500. Прогрев: готовность worker canvases и ещё 1200 мс; измерение — 3 секунды. До изменений — три повтора; после — два для полей, обводок и QuantumField, три для композиции. Это короткие steady-state пробы, не длительная гарантия FPS и не измерение холодного открытия.

Исправления:

- Общий clock и workers по умолчанию получают цель 60 вместо 20/30 fps. При 60 убрано дополнительное ожидание таймера перед requestAnimationFrame. Явный `setMotionFrameRate(30)` и остановка скрытых/неиспользуемых эффектов сохранены.
- NeonWaves рисует звёзды в существующем worker вместе с волнами. Позиции, размеры, девять фаз и CSS ease-in-out сохранены. При отсутствии worker canvas действует CSS fallback с девятью группами вместо 60 отдельных анимаций. Пауза вне экрана охватывает корневой элемент, включая звёзды.
- QuantumField больше не ограничивает WebGL собственными 24/30 fps. Допуск 0,5 мс предотвращает пропуск кадров из-за округления timestamps. CPU fallback сохраняет прежнее ограничение; QuantumBackground остаётся отдельным адаптивным визуализатором.

Частота общего clock измерена отдельно; у QuantumField дополнительно считались реальные вызовы очистки WebGL canvas: после изменений около 60/с на обоих уровнях замедления против примерно 20–21/с до изменений. Переход на более частое обновление сам по себе увеличивает работу: на ×16 медиана main thread для полей выросла 1522 → 1947 мс (+27,9%), обводок 1556 → 2252 мс (+44,7%), QuantumField 1449 → 1952 мс (+34,7%). На ×8 соответствующие изменения: 520 → 672 (+29,2%), 537 → 742 (+38,2%), 411 → 730 мс (+77,6%). Это плата за частоту, а не снижение CPU. При 90 обводках на ×8 появились пропущенные кадры по сравнению с baseline; общий clock при этом обновлялся значительно чаще. Для приложений, предпочитающих меньше декоративной работы, остаётся явная настройка частоты.

Отброшенные варианты: одно увеличение частоты перегружало CSS-звёзды; группировка уменьшила нагрузку, но на ×16 оставалась недостаточной. `will-change` для звёзд/групп, CSS transform индикатора и отключение его фильтра не стали производственными изменениями. Перенос звёзд в существующий worker устранил этот bottleneck. До переноса проверены 180 значений композиционной opacity: максимальное отличие от прежнего CSS — менее 0,000001. Worker отдельно проверяется по координатам, размеру и значениям easing в начале, середине и конце цикла.

Ограничения: непрерывные минимум 60 fps не достигнуты во всех стресс-сценариях. Есть отдельные длинные кадры, включая 133 мс в композиции на ×16. Одна промежуточная серия прервалась по тайм-ауту готовности 90 обводок; последующая серия из двух повторов завершилась, тайм-аут не считается успешной проверкой. CPU-only диагностический прогон QuantumField на ×16 дал около 21 кадра отрисовки/с и 34 rAF/с; его нельзя выдавать за 60 fps. GPU/VRAM utilization, пиковая RAM, реальные iGPU/малоядерные устройства, event-to-paint latency и длительная стабильность не измерены. JS heap в raw JSON — моментальный снимок, не пик памяти. Частота пиксельной отрисовки OffscreenCanvas workers отдельно не измерена.

## MelodyRoll

Найдена и изменена существующая реализация `packages/ui/src/components/media/MelodyRoll`: два производственных файла, 35 добавленных и 12 удалённых строк. Клавиатура уже использовала memo; новый компонент или отдельный планировщик не добавлялись.

На каждом playback update раньше создавался массив всех pitch, пересчитывались границы и фильтровалась вся песня. Теперь при смене `notes` рассчитываются pitch bounds и временные границы блоков по 128 нот; кадр проверяет только потенциально видимые блоки. Исходный порядок и длинные перекрывающиеся ноты сохраняются. Для хаотично перемешанных нот худший случай остаётся линейным. Массив и его ноты должны обновляться иммутабельно. Лента привязана к ближайшему временному окну, чтобы координаты обычных нот не росли вместе с длительностью песни.

Главный браузерный bottleneck — RecalcStyle при постоянно меняющихся beat/accuracy/level. Точность и громкость перенесены с корня на след и маркер голоса. Beat зарегистрирован как ненаследуемое числовое свойство, с явной передачей двум использующим его псевдоэлементам. Остальные ноты и клавиши не наследуют эти обновления. Свечение, переходы, попадания, текст, колесо и диапазоны высоты сохранены. Отключение transitions давало дополнительное ускорение, но этот вариант не принят из-за изменения визуального поведения.

Сценарий: один MelodyRoll 1400×400, 10 000 нот с шагом 0,25 с, длительностью 0,2 с и диапазоном 60–71 MIDI; около 32 видимых нот, lyrics включены. Position, livePitch, accuracy, level и beat обновляются общим clock. Production React, Chrome и компьютер те же. CPU ×8/×16 — эмуляция. Два прогретых окна примерно по 3 секунды на каждую частоту, в подтверждающей серии сначала итоговая версия, затем baseline. Baseline подставляет **только MelodyRoll.tsx и styles.css из HEAD**, проверяет наличие обоих файлов; общий scheduler одинаков. `rendererFrames` в этом сценарии считает React commits, не физические презентации GPU.

### Дополнительная диагностика MelodyRoll

Раздельные обновления входов на ×16 локализуют затраты браузера. Это одиночные диагностические окна по 3 секунды, а не сравнение производственных версий; остальные входы заморожены, React продолжает получать clock updates.

| Меняющийся вход (`FRAME_MELODY_INPUT`) | rAF FPS |
|---|---:|
| none — все входы постоянны | 60,0 |
| position | 10,8 |
| voice — livePitch | 21,8 |
| accuracy | 27,5 |
| level | 28,4 |
| beat | 18,2 |
| all | 6,1 |

Raw данные: `melodyDiagnostics` в performance-results.json. Трассировка включается через `FRAME_TRACE=1`, сохраняется рядом с JSON в `.trace.json`. Дополнительные CSS overrides задаются `FRAME_EXTRA_CSS`; они диагностические и не входят в компонент. Скрипт записывает выбранный вход, overrides и флаги диагностики, чтобы результаты нельзя было принять за полный сценарий.

Повторный полный прогон без overrides, окна по 5 секунд: ×8 — 35,4 FPS, p95 50 мс, max 83,5 мс; ×16 — 6,3 FPS, p95 266,6 мс, max 433,4 мс (`melodyDiagnostics.confirmation`). Разброс ×8 между сериями не считается ускорением: производственные файлы идентичны началу этой серии. Синтаксис benchmark проверен `node --check`; `git diff --check` прошёл. Повторная сборка и suite на этом диагностическом этапе не запускались, поскольку производственные изменения экспериментов отменены.

В трассе пересчёт стилей затрагивает около 21–23 элементов. Chrome сообщает причины отказа compositor animations: 4096 для перемещающих пиксели фильтров и 8224 для неподдерживаемых CSS-свойств вместе с invalid compositing state. Соответствие кодов проверено по [CompositorAnimations](https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/core/animation/compositor_animations.h); ограничение фильтров — по [реализации Chromium](https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/core/animation/compositor_animations.cc). Аппаратная композиция и растеризация включены; активный ANGLE renderer использует NVIDIA RTX 3060/D3D11. Причина не сводится к отсутствию GPU.

Изучены [обсуждение SVG drop-shadow](https://stackoverflow.com/questions/19565622/css-animation-performance-issues-using-svg-drop-shadow-filter) и [обсуждение box-shadow в Lighthouse](https://github.com/GoogleChrome/lighthouse/issues/15560). Советы про статическое свечение и анимацию opacity требуют проверки визуальной эквивалентности: замена меняющегося радиуса размытия прозрачностью постоянной тени изменяет эффект. Такая замена не принята.

Проверены дополнительные `will-change`, containment, прямой transform секундной сетки, memoization частей компонента и перенос вертикального движения маркера на translate. Убедительного прироста полного сценария они не дали; производственная реализация после этой серии сохранена без этих изменений. Незавершённый прототип canvas renderer удалён. Новый прирост производительности не заявляется; цель 60 FPS на ×16 остаётся недостигнутой. Следующая проверяемая гипотеза — кэширование/отрисовка динамического свечения вне основного потока с сохранением его формы, цветов и переходов; визуальная эквивалентность такого подхода пока не доказана.
